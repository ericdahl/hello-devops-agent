01The one-paragraph version

AWS DevOps Agent is a hosted agent loop that AWS runs on your behalf. You give it a cross-account IAM role and some integration credentials; it crawls your accounts with Resource Explorer and builds a topology graph of your resources and their relationships. When an incident arrives — via webhook, or you ask it a question — it runs a tool-calling loop over CloudWatch, CloudTrail, your Git history, and whatever observability vendors you connected, forms hypotheses about the cause, tests them with more queries, and writes up findings with a suggested fix. You pay per second of agent wall-clock time.

The genuinely new part is not the LLM. It is the pre-built read integration layer — the topology graph, the vendor connectors, the account-assume plumbing — that you would otherwise spend months wiring up yourself.

04What one investigation actually does

This is a real sequence, not a feature list — each step feeds the next.

  1. TriageDecide whether this incident is worth investigating at all. Your triage skills can define skip criteria (maintenance windows, severity floors). Skipped incidents get a stated reason.
  2. Ground in topologyLook up the alarming resource in the pre-built graph to get blast radius immediately, instead of discovering dependencies mid-incident.
  3. Correlate telemetryPull logs, metrics, and traces around the incident window across every associated account and region.
  4. Diff what changedCloudTrail config changes, recent deployments, Git commits. This is where the GitHub/GitLab integration earns its keep — "what shipped in the last hour" is the highest-yield question in most incidents.
  5. Hypothesize and testForm a candidate cause, then issue more read queries to confirm or kill it. This loop is the part you are paying per-second for.
  6. Write upRoot cause with supporting evidence, plus a ranked mitigation plan. Routed to Slack / ServiceNow / PagerDuty if connected.

05Read vs. write — the part worth being precise about

The default posture is read-only. The managed policy AIDevOpsAgentAccessPolicy grants describe/get/list across CloudWatch, Logs, Config and friends, plus one narrow write: iam:CreateServiceLinkedRole for Resource Explorer. Registered MCP servers are required to expose read-only tools. AWS's own production guidance says explicitly to avoid granting modify or delete permissions.

Unresolved

The marketing page says the agent "provides specific remediation actions, validates success, and can rollback changes if needed," and there is an Incident Mitigation agent type. But the FAQ and IAM guidance describe investigation and recommendation only. My read: mitigation is plan-and-approve, and any actual write happens through a mechanism you grant separately. Worth confirming hands-on before you trust either description.

06Where AgentCore actually fits

Both are AWS agent products and the naming invites confusion, so: AgentCore is the platform this is built on, not something you touch. You never see a Runtime container, a Gateway, or a Memory store. There is no Python handler to write. DevOps Agent is a finished SaaS product that happens to be implemented on AgentCore internally, in the same way an RDS instance happens to run on EC2.

Your extension points are deliberately narrow and none of them are AgentCore APIs:

  • Skills — Markdown instructions that shape how it investigates.
  • MCP servers — your own read-only tools, over public HTTPS, registered per account and allowlisted per space.
  • Integrations — the supported connector list.

If you want to build an arbitrary agent, that is AgentCore. If you want an on-call teammate that already knows how to read CloudWatch, that is this.

07What it costs, concretely

$0.0083 per agent-second, billed per second, only while the agent is working. Idle time and topology mapping are free. That is $0.498/min, $29.88/hr.

Free trial

Two months for any account new to DevOps Agent, regardless of account age: up to 10 agent spaces, 20 hours of investigations, 15 hours of evaluations, 20 hours of on-demand tasks. Plenty for a hello-world.

No cost cap

There is no ceiling on per-incident spend. A noisy alarm wired straight to the webhook with no triage skill is an open tap. Put a budget alarm on it before you point anything real at it.

Separately: paid AWS Support plans get monthly credits against DevOps Agent — 100% of the prior month's support charge on Unified Operations, 75% on Enterprise, 30% on Business+. They expire monthly and don't roll over. Underlying CloudWatch and trace-retrieval calls are billed normally.

08The honest limitations

It correlates better than it concludes

The sharpest independent finding: in a test where a Lambda's TABLE_NAME env var pointed at …-inventory-v1 while its IAM policy granted …-inventory, the agent found both halves of the mismatch and then recommended fixing the wrong one. Following it would have traded an AccessDeniedException for a ResourceNotFoundException. It is excellent at assembling every relevant fact; deciding which side of a mismatch is the bug is still yours.

CloudWatch alarms don't connect natively

Despite CloudWatch being the flagship integration, there is no alarm action target for DevOps Agent. You write a bridge Lambda: read webhook URL and HMAC secret from Secrets Manager or SSM, build the incident payload, sign it, POST it. The webhook URL itself is generated in the console and cannot be provisioned by IaC. That is a real gap between the pitch and the setup.

Output quality is capped by input coverage

It can only reason over what you connected. Thin instrumentation in, thin analysis out. Multicloud is real but shallow — Azure correlation works, with noticeably less depth, and there is no CloudTrail equivalent to lean on.

Operational sharp edges

  • SCPs must permit aidevops:* and bedrock:InvokeModel, or investigations fail with a correctly configured space.
  • Trust policy aws:SourceArn must match the agent space ARN — wildcards where an exact ARN is expected return 400.
  • Skill zips reject anything in scripts/ unless Sandbox preview is on. 6 MB, 100 files max.
  • The Slack app showed "not approved by Slack" during OAuth as of mid-2026. Functional, but your security team will ask.
  • Bedrock may perform stateless inference in US regions other than your space's region — relevant if you have data residency requirements.

09Hello-world, when you want it

Check first that your credentials actually reach the service — aws devops-agent list-agent-spaces should return rather than deny, and aws cloudformation describe-type --type RESOURCE --type-name AWS::DevOpsAgent::AgentSpace should resolve in a supported region. An empty space list also means the free trial is still intact. Admin in the target account is the simplest starting point; a scoped user without aidevops:* will fail at the first call.

The shape of the smallest end-to-end demo:

  1. Terraform the spaceTwo IAM roles (agent + operator app), one AgentSpace, one Association of type monitor pointing at this account. Trust principal is aidevops.amazonaws.com with both aws:SourceAccount and aws:SourceArn conditions.
  2. Deploy something breakableA Lambda that publishes to an SNS topic it lacks permission for. Deterministic, instant, and a genuinely realistic failure mode.
  3. Wire the triggerGenerate the webhook URL in the console, store URL + HMAC secret in Secrets Manager, then: error metric → CloudWatch alarm → bridge Lambda → signed POST.
  4. Break it and watchInvoke the failing Lambda, wait for the alarm, then read the investigation in the operator web app. Compare its conclusion against the bug you planted.
  5. Add a skillWrite one SKILL.md for this service and re-run to see how the investigation changes. This is the highest-signal part of the exercise.

AWS publishes both halves as samples: sample-aws-devops-agent-cdk for the space, and sample-aws-devops-agent-cloudwatch for the alarm→webhook bridge. Both are CDK/SAM; a Terraform version is straightforward and closer to how you work.
